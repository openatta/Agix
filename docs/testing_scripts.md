# 脚本载体的回归网

QuickJS 脚本能绑上去的九个点，怎么被测。

这份文档讲的是设计——为什么这张网是这个形状、一条用例要满足什么才算数、加新用例
该往哪儿加。载体本身怎么用见 `extending_quickjs.md`，测试系统的全景见
`../tests/README.md`。

## 一个硬约束先说在前面

脚本每次调用拿到一个全新的运行时，调用之间什么都不留；没有 `require`、没有
`fetch`、没有文件系统。所以**脚本没法给自己记账**：「这个点被触发了吗」这个问题，
脚本自己回答不了，它唯一的表达渠道就是在自己那个点上的返回值。

于是观测只能从外面做，而外面只有三个面：

| 观测面 | 看得见哪些点 |
|---|---|
| 到达 `Model` 的请求 | `prompt.*`、`model.request`；`model.message` 在下一轮；`memory.retrieval_hook` 的结果 |
| 会话日志 | 消息被记下来时的样子 |
| 工作目录终态 | `tool.around` 有没有真的拦下派发 |

这三个面能回答「脚本生效了吗」，但回答不了「脚本没生效是因为什么」。而载体承诺的
语义恰恰是**失败的脚本什么都改不了**——于是「脚本抛了异常」和「脚本压根没绑上」
在外面看起来一模一样。一张分不出这两者的网，会以错误的理由通过。

## 账本

`ScriptLedger` 补的就是这个。它不是给脚本的 API，是载体侧的记录器：每个适配器在
决定完自己这次要不要施加改动之后，往账本里追加一条。

```
{ point, script, entry, turn, outcome }

outcome ∈ Applied            脚本跑了，改动施加了
        | NoChange{detail}   脚本跑了，按这个点的契约没有可施加的东西
        | Failed{error}      调用本身没完成：抛异常 / 超时 / 配额耗尽 / 没有引擎
        | Refused{detail}    脚本要求的事，它的出身不允许
```

由适配器写而不是由载体写，是因为只有适配器知道最后那一步：载体看得见调用成功与
否，看不见返回值有没有被采纳。`prompt.assemble` 一次调用可以产出多条记录——被拒
的每条编辑一条 `Refused`，最后一条 `Applied`——因为那个点本来就允许「一部分获准、
一部分被拒」。

账本随 `BoundScripts` 一起产出，容量有上限，并记录被挤掉的条数：一条读不到的记录
和一条不存在的记录必须分得开。

它不只服务测试：daemon 把每个会话的账本挂在 `session.get` 的 `scripts` 字段上，
所以「我的脚本怎么没生效」这个问题，运维者自己就能回答——四种「没生效」在引擎里
效果完全一样，只有账本分得出是哪一种。

## 两层

两个诉求在确定性上是相反的。「插件动作有没有被触发」是确定性事实；「任务完成得
正不正常」一旦交给真模型判断就不是。所以模型那一端一律写死：

| 层 | 驱动 | 回答什么 |
|---|---|---|
| L1 契约 | 脚本化模型 | 每个点单独：绑上生效、不绑不生效、坏掉不害人 |
| L2 任务 | 脚本化模型 + 真工具 + 真文件系统 | 九个点同时在场时，一件真活儿的终态 |

**全部进 `cargo test`，全部不联网、不要凭据。** 曾经还有第三层：拿真模型跑几条用例、
把交互录下来回放。它退休了，理由和 `test_runner::scripted_model` 模块头写的是同一个
——录像烘进了精确的提示词，提示词一改就全挂，所以它从来不能当可提交的回归网；而不能
提交、不能在 CI 里跑的那一层，价值取决于有没有人记得手动跑它。

代价要说清楚：**「模型自己会怎么选」这个问题现在没有测试回答。** 脚本化模型的下一步
是写死的，所以「脚本拒掉 Bash 之后模型会不会换一条路」这类问题，只能靠人手工验。
知道这个空档在哪儿，比留一批放不了的录像假装它被覆盖了要好。

## 一条用例要满足什么

**能失败。** 差分对照是最低要求：同一段会话跑两遍，一遍绑脚本一遍不绑，其余完全
相同。没有第二遍，「痕迹在请求里」也可能是它本来就一直在。

**痕迹携带「这是哪一次调用」。** 脚本无状态，但输入里有可推导的量：
`model.request` 有 `messageCount`，`tool.*` 有工具名和参数，`prompt.context` 有
`cwd` 和 `date`，召回钩子有 `phase`。`SCRIPT-TRACE-RESULT(ScriptEcho)` 和
`SCRIPT-TRACE-CONTEXT: working in <cwd>` 已经是这么写的：后者带的 `cwd` 身份调用
看不见，所以一个「绑定期就注册了静态文本」的假实现会被它抓住。一个常量痕迹只能
证明「跑了」，带上输入才能证明「在正确的时机对正确的输入跑了」。

**两条腿一起断言：插件效果 + 任务终态。** 而且终态要挑脚本**不该**影响的那部分。
只断言痕迹的用例证明不了「插件没有破坏任务」，而那正是要问的第二个问题。

**正例只占一半。** 正例挂了当天就发现；边界例——失败隔离、配额、超时、权限、绑定
失效——挂了要等到事故。回归网的价值几乎全在后者。

## 用例矩阵

### A · 单点契约

九个点，每个点三个变体：**生效 / 不绑 / 脚本坏掉**。第三个变体断言这个点保持原样、
账本记 `Failed`、并且**这一轮照常跑完**。

`prompt.assemble`、`prompt.block`、`prompt.context`、`prompt.variable`、
`tool.around`、`tool.result`、`memory.retrieval_hook`、`model.request`、
`model.message`。

断言的形状不止一种，所以用例表说的是期望而不是一个痕迹字符串：

```
MarkAppears(mark)     绑上时这个痕迹到达模型，不绑时不到达
ToolWithdrawn(name)   绑上时请求不再提供这个工具，不绑时提供
```

`model.request` 拿到的是旋钮和工具**名字**，不是消息，所以它能做的事里唯一在请求
里看得见的就是少提供一个工具——表达不成「痕迹出现」。用例表原本只能表达出现，这个
点因此一条端到端用例都没有。

坏脚本那一档不看请求看账本：它要证明的恰恰是「没有任何可观察的事情发生」，而那和
「压根没绑」在请求里长得一模一样。

### B · 交叉

单点用例证明每个适配器自己是对的，交叉用例证明它们放在一起还是对的。这是重构最
容易碰坏、而单点用例一条都抓不到的地方。

1. `tool.around` 返回 `respond` 之后，`tool.result` 还跑不跑。契约没规定，答案是
   什么都行，但必须钉死一个。
2. `tool.around` 返回 `deny` 之后，模型看到的那条错误文本会不会再被 `tool.result`
   改写。
3. `prompt.block` 注册的块被 `prompt.assemble` 删掉——注册与拦截的先后。
4. 一个脚本的 `prompt.variable` 出现在另一个脚本的 `prompt.block` 正文里。这是唯一
   一个必须两个脚本协作才成立的点。
5. `model.request` 把某个工具从 `tools` 里删掉，而模型偏要调它。引擎的行为必须确定，
   且任务不能崩。
6. 同一个点上两条绑定的顺序：`tool.around` 上第一条是最外面那一环。
7. `model.message` 改写第 N 轮的回答后，第 N+1 轮的请求看到改写后的那份，**会话
   日志里记的也是改写后的那份**。两者不一致会在 resume 和 fork 的时候变成一个极
   难查的 bug。
8. 召回钩子的两半在**每一轮**都跑，而不是一个会话一次。账本里的轮次号是唯一能
   看出差别的地方——一个只装一次、只问一次的钩子，在所有单轮用例上都是对的。

### C · 边界与安全

全部是载体已经声明过的承诺。这一档单独一个文件，因为它挂掉的时候不该有人想「重新
生成一下黄金文件算了」。

| 承诺 | 用例 |
|---|---|
| 一条绑定失效则一个脚本都不绑 | 四条绑定，其中一条指向没有适配器的点；另一条指向不存在的文件。两种都要求整组作废，且错误点名是哪一条 |
| 项目外的脚本只能新增 | 脚本放在项目根之外，一次调用里既新增又改写：新增生效、改写被拒、拒绝进账本。同一个脚本挪进项目根之后两样都放行 |
| 死循环也能被停下来 | `while (true) {}` 配 50ms 预算：工具结果原样到达模型，账本记 `TimedOut` |
| 配额按绑定计、每轮重置 | 配额 2 而这一轮有 3 次工具调用：两次 `Applied` 一次 `QuotaExhausted`，下一轮重新可用 |
| 内存 16 MB | 不断增长的脚本配 5 秒预算——失败的是天花板不是时钟，另一个点的脚本照常贡献 |
| 形状不对 = 保持原样 | `model.message` 返回长度不匹配的数组；`prompt.variable` 返回数字，占位符原样留在提示词里 |
| 内核块名被拒绝 | 脚本注册 `rules`，不能把本该落在真块上的编辑吸走 |
| 环坐在权限闸门外面 | `ask` 模式 + 一个总是要审批的工具：脚本拒掉之后，审批问题**一次都没被问出来**；不绑脚本时同一个调用确实会问 |
| 脚本不热加载 | 两轮之间改掉脚本文件，第二轮仍然是旧行为——skill 和 agent 类型都有 watcher，脚本故意没有 |
| 绑定只读文件不求值 | 语法错的文件绑得干干净净，之后每次调用各自失败——和路径打错是两种不同的坏日子 |
| 每条绑定各有各的预算 | 同一个文件绑两个点、各给配额 1：两个点的第一次调用都成功，说明预算没被共用 |
| entry 名字写错 | 注册点在绑定期什么都不注册；拦截点每次调用失败，工具结果原样通过 |
| 重排表达不出来 | 原样倒序交回：什么都没被改写（同名块的编辑落不到指定的那一个身上，会被拒绝而不是错落到第一个） |

**曾经不在这张网里的那一条**：没有载体的构建拿一个 `scripts` 段怎么办。一个「带着
载体」的构建跑出来的测试观测不到「不带载体」的那个构建——除非被测的 daemon 是另一
个进程。`tests/daemon_harness` 就是干这个的：同一个项目、同一份 settings，分别喂给
默认构建和 `--no-default-features` 构建，前者痕迹到达提示词且 `session.get` 有账本，
后者两样都没有。

两半都要断言。痕迹不见了只说明脚本没跑；`session.get` 连 `scripts` 键都没有才说明
**没有东西能跑它**——而「跑了但什么都没改」和「压根没人跑」的区别，在有载体的构建里
靠账本分，这恰好是账本不存在的那个构建。

### D · 四剖面金任务

L2 的主体。一件小而真实的活儿，终态完全确定：读 `src/main.py`、改掉一个错字、再读
一遍确认。真工具、真工作目录，模型的每一步由脚本化回复钉死——任务本身在四个剖面之
间必须一模一样，否则分不清「脚本破坏了工作」和「模型这次选了别的路」。

| 剖面 | 绑定 | 断言 |
|---|---|---|
| 无 | 什么都不绑 | 活干完了（基线） |
| 观察者 | 九点全绑，都不改变结果 | 工作目录与基线**逐字节相同**，九个点各自都有 `Applied` 且无 `Failed` |
| 干预 | 同上，但工具环拒绝 `Edit` | 文件停在改之前；文件集合与轮次形状和基线一致；模型被告知了拒绝的理由 |
| 全坏 | 九点全绑，全部抛异常 | 工作目录回到基线；九个点的记录**全部**是 `Failed` |

第五条用例问的是派生：策略脚本跟着子 agent 走，提示词脚本不跟。它靠磁盘断言——不
继承的话，子 agent 会把那次被拒的编辑做掉。

要害在观察者剖面和全坏剖面**留下同一个目录**：一个是全都跑了且无害，一个是全都死了。
磁盘上分不出来，和「压根没绑脚本」也分不出来——差别只存在于账本里。这就是账本不是
诊断工具而是承重断言的原因。

**没有黄金文件。** 基线是在同一次运行里现算的，所以没有会过期的文件，也没有可以被
反射式重新生成的东西；任务本身由脚本化回复钉住。

## 放在哪

脚本 fixture 全部在 `tests/fixtures/scripts/` 下，每个留一处引擎别处绝不会产生的痕迹：

```
tests/fixtures/scripts/
  <point>.js              九个点各自的观察者
  tool_around_observe.js  只放行、不改变结果的环（供全绑剖面用）
  tool_around_deny_edit.js  干预剖面里唯一真的改行为的那个
  broken/                 抛异常、死循环、吃内存、形状不对、抢内核块名
tests/fixtures/scripts_outside/   故意放在项目根之外，用来验出身判定
```

剖面是 Rust 里的一张表，不是磁盘上的配置：绑定组合本来就是用例的一部分，写成 JSON
sidecar 只会让「这一组为什么这么绑」离断言更远。

| 层 | 文件 |
|---|---|
| A、B | `tests/runner/tests/script_carrier.rs` |
| C | `tests/runner/tests/script_boundaries.rs` |
| D | `tests/runner/tests/script_task_profiles.rs` |
| daemon 那条路 | `daemon/tests/session_lifecycle.rs` |
| 装配好的那条路 | `tests/daemon_harness/tests/daemon_surface.rs` |

daemon 的两条单独在那边：从 `.agix/settings.json` 到装到会话上的这一段全是 daemon
的活——解析、按项目根解析路径、每个会话绑一次——驱动 `Builder` 的用例问不到它。

`daemon_harness` 那几条又低一层：进去是 JSON-RPC，出来是一个说 Anthropic SSE 的
HTTP 桩，所以「脚本改的东西到没到模型」是从**桩收到的那个请求**里读出来的，不是从
引擎内部的某个中间值。每条跑两遍，本进程和另起一个 `agixd`。

| 用例 | 问什么 |
|---|---|
| `a_bound_script_reaches_the_prompt_and_the_ledger` | 项目 settings 绑的脚本，痕迹到达提示词、账本记 `applied` |
| `a_packaged_script_runs_beside_the_projects_own` | `plugin.install` 装进来的包里那个脚本**真的被调了**；它和项目的脚本共用一份账本（也就是共用一份每轮预算），账本靠路径把两种出身分得开 |
| `a_package_may_add_to_the_prompt_but_not_rewrite_it` | 出身这条规则活过了整条装配路径：包的改写被拒、记成 `refused` 且带理由，项目自己那条照常 `applied` |
| `a_build_with_no_script_carrier_honors_no_scripts_section` | 不带载体的构建拿到 `scripts` 段：痕迹没有，`session.get` 连 `scripts` 键都没有 |

C 档里「项目外的脚本只能新增」问的是同一条规则，但那是在 `Builder` 那一层拿一个放在
项目根外面的文件问的。这里问的是**一个真的装进来的包**——manifest 解析、解包落到
版本化缓存、绑定按包的 root 判定出身——中间任何一步把出身弄丢了，C 档都看不见。

驱动会话的那段代码在 `tests/runner/src/script_session.rs`——三个二进制共用一个，
各写一份会漂，而漂了的驱动比没有测试更糟：它会持续报告一个并不存在的引擎。

每个集成测试文件是一个独立二进制，静态链接整张依赖图，约 190 MB（见
`../tests/README.md` 的磁盘一节）。这就是为什么 A 和 B 合在一个文件里，而不是按
概念各占一个。

## 加一条用例

**加一个点的单点用例**：在 `tests/fixtures/scripts/` 放一个 fixture，给它一个别处
绝不会产生的痕迹，在用例表里加一行。一个还没有适配器的点没有行——断言「未绑定的点
什么都不改」会以错误的理由通过。

**加一条交叉用例**：它必须是两个点的**相互作用**，而不是两个点各自的行为。判据是
把其中一个点去掉之后，这条用例还成不成立；还成立说明它是一条单点用例。

**加一条边界用例**：先在 `extending_quickjs.md` 里找到那句承诺。找不到就先去写那句
承诺——一条不对应任何承诺的边界用例，钉住的是当前实现，不是设计。

## 不在这张网里

**hooks** 是另一个子系统，另一套进程模型，成本和抖动都不同。目录里其余的点是构建期
接好的 Rust trait，脚本没有注册入口，不属于这张网要回答的问题。

**WASM 插件**与脚本是互斥的 feature，一个构建只带一个载体，同时开编译不过，所以它
确实不在这张网里——但它有自己的那张：`crates/wasm-host/tests/component_roundtrip.rs`
拿真组件问载体本身（超时、陷阱、能力、状态不外泄），`crates/plugin-host` 问一份
manifest 怎么变成注册好的工具，而**装配面**六条在
`tests/daemon_harness/tests/daemon_surface.rs`：

| 用例 | 问什么 |
|---|---|
| `a_wasm_plugins_tool_is_called_and_answers` | 一个包带着组件装进去、模型调它的工具、guest 的答案回到模型 |
| `a_plugins_tools_are_offered_to_every_session` | 那些工具到底进了哪些会话（答案是：所有会话，包括内建场景的） |
| `a_trapping_component_costs_its_call_and_not_the_turn` | 陷阱只赔那一次调用，同一插件的下一次照常 |
| `a_plugin_that_keeps_faulting_is_set_aside` | 连续三次故障之后整个插件被搁置——最后一次问的是一个能用的工具，它也被拒 |
| `a_capability_the_package_never_declared_is_unreachable` | 没声明的能力够不着，理由点名它到达模型；披露里也没吹过 |
| `a_build_with_no_plugin_carrier_installs_but_does_not_run` | 没有引擎的构建：装得上、披露说组件不会跑、一个 `plugin__` 工具都不给模型 |

除最后一条外都要一个带载体的 daemon（测试二进制自己编的是默认载体，进程内没有引擎
能跑组件），CI 在 `test` job 里另建一个并用 `AGIX_TEST_DAEMON_BIN_PLUGINS` 指过去。

两个载体的**覆盖形态**对齐了，**行为**没有、也不该：脚本的权限分岔看文件在哪，插件
看装时声明了什么；脚本绑到具体的点，插件的工具进每个会话。还有一处是真差距——脚本
有 `session.get` 的账本说得清「这次为什么没生效」，插件今天没有对等的 RPC 可观测面。
